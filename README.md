# pipeline-etl

An incremental ETL framework in Python: watermark-tracked windows, idempotent
loads, and data-quality validation that quarantines bad rows rather than failing
the batch. **48 tests**, no database needed to run them.

```bash
python example.py    # a full run, in memory, no setup
```

The two problems this is built around are the ones that actually cause incidents
in a nightly load.

## 1. Incremental loading without losing or duplicating rows

Two mistakes are easy to make and hard to notice:

**A strict `>` on a timestamp watermark silently drops rows.** If the last run
ended at `12:00:00` and three rows share that exact timestamp, starting the next
run *after* it skips them permanently. This overlaps each window backwards by a
configurable lookback (five minutes by default) and relies on the load being
idempotent, so re-reading is free.

**Advancing the watermark before the load commits loses data.** A crash in between
means the batch is never retried. Here the order is fixed: extract, validate,
load, *then* commit the watermark. Any failure leaves the watermark where it was
and the next run reprocesses the same window.

```
run 1:  [11:00 ────────── 12:00)   commit → watermark = 12:00
run 2:        [11:55 ────────────── 13:00)   commit → watermark = 13:00
              └ overlap, deduplicated by the primary key
```

The loads are `INSERT ... ON CONFLICT (key) DO UPDATE`, generated by
`upsert_statement()`, which is what makes the overlap harmless. The example above
sends 38 rows across two runs and leaves 19 in the table.

A watermark is also never moved backwards — rewinding it would make every later
run reprocess the gap.

## 2. One bad row should not block a thousand good ones

Aborting on the first malformed record means one bad row holds up the entire
batch. Dropping it silently means nobody finds out. Neither is acceptable, so:

- Rows failing validation go to a **quarantine table with the reason attached**,
  stored as JSONB so a feed that changes shape still lands somewhere inspectable.
- Good rows load normally.
- The run fails **only if the rejection rate crosses a threshold** (5% by default).
  That is the signal distinguishing "one odd record" from "the upstream feed
  changed", and in that case the watermark is left alone so the window retries
  after a fix.

```python
validator = Validator(
    {
        "id": [required],
        "amount": [required, is_decimal, non_negative],
        "currency": [required, one_of(["php", "usd"])],
    },
    error_threshold=0.10,
)
```

Each row collects *every* reason it failed, not just the first, so one pass
through the quarantine table tells you everything wrong with a record.

## Using it

```python
runner = PipelineRunner(
    PostgresLoader(dsn),
    WatermarkManager(PostgresWatermarkStore(dsn), lookback=timedelta(minutes=5)),
)

report = runner.run(PipelineSpec(
    name="sales",
    table="fact_sales",
    columns=["id", "store_id", "sold_at", "amount", "currency"],
    key_columns=["id"],
    extractor=lambda window: fetch_sales(window.start, window.end),
    validator=validator,
))

if not report.succeeded:
    alert(report.error)
```

`RunReport` carries the counts, the window, whether the watermark advanced, and
the error if there was one — enough to drive alerting without parsing logs.

```bash
psql "$DATABASE_URL" -f sql/schema.sql   # watermarks, quarantine, example target
pip install -r requirements.txt
```

## Tests

```bash
python -m pytest tests/ -q      # 48 tests
```

Postgres is faked in memory, so the suite runs anywhere. The cases that matter:
a failed load leaving the watermark untouched and the next run reprocessing the
same window; the overlap re-sending rows that the upsert absorbs; a threshold
breach aborting without committing; an extractor raising being reported rather
than crashing the scheduler; and an empty batch still advancing the watermark, so
an idle period does not make the window grow without bound.

## Layout

```
pipeline/
  watermark.py    windows, watermark commits, upsert generation
  validation.py   per-column checks, quarantine partitioning, thresholds
  runner.py       orchestration and the commit ordering
  loaders.py      Postgres loader and watermark store
sql/schema.sql    warehouse objects
example.py        runnable demonstration, no database
tests/
```

## Known limits

- Single-process and single-threaded. Parallel windows per pipeline would need a
  lock so two runs cannot commit watermarks out of order.
- `executemany` is fine for thousands of rows per batch; past that, `COPY` into a
  staging table and a single `MERGE` is substantially faster.
- Watermarks are timestamp-based. A monotonic sequence or log position is more
  robust where a source can write rows with an older timestamp than one already
  seen.
- No scheduler. It is meant to be invoked by cron, Airflow or similar rather than
  managing its own timing.
- No schema-drift detection: a new upstream column is ignored rather than flagged.
